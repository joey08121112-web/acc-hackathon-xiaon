# ADR-001 · 插件不是插件：目录约定就是机制本身

- **状态**：生效（2026-11-21 记录，2026-11-21 起依赖方向已清理）
- **相关代码**：`server/plugins/`、`server/agents/learning.ts`、`server/bootstrap.ts`

## 背景

`server/plugins/` 下有 12 个目录，看上去像一套插件体系。但全项目**只有两处引擎注册**
（`server/bootstrap.ts` 的 `registerAssessment` / `registerPlanning`），**没有任何插件注册入口**：

- `assessment` / `planning` / `generation` 是 class，其余 9 个是裸导出函数，
  由 `agents/learning.ts` 静态 import；
- ctx 形态不统一：只有 `RevampContext` 与 `ProfessionalContext` 两个手写 interface，
  插件另配 11 种自定义 Input 类型；
- **新增一个插件要改 5 处**：契约加 schema → `repository.ts` 的 `entitySchemas` 加一项
  → 写插件 → `learning.ts` 加 import + `perform()` → `http/server.ts` 加路由。
  **没有任何一处会自动发现新插件。**

## 决策

**不引入插件框架。** 12 个插件还没多到需要框架的成本，而框架本身会引入
「插件怎么拿到 repository / 怎么声明权限 / 出错怎么办」这一堆新的设计问题 ——
在还没被真实需求逼出来之前先设计，是典型的过度工程。

但**必须把这件事写下来**，否则下一个人会以为「往 `server/plugins/` 扔个目录就注册好了」，
然后花半天找「注册入口在哪」。

## 后果

- **写新插件的完整清单**（照这五步做，不多不少）：
  1. `shared/learning-contracts.ts` 里加 schema，放进 `schemas`；
  2. `server/storage/repository.ts` 的 `entitySchemas` 加一项
     —— 若实体带 `revision` 字段，它会自动进 `revisioned` 集合（2026-11-21 起从契约派生，不用手改）；
  3. 在 `server/plugins/<名字>/` 写实现，导出明确的函数或 class；
  4. `server/agents/learning.ts` 静态 import，并在 `perform()` 里接上；
  5. `server/http/server.ts` 加路由。
- **依赖方向**（2026-11-21 清理后）：`shared/` ← `server/core/` ← `server/plugins/` ← `server/agents/`。
  曾经存在的 `plugins → agents` 反向依赖（6 条：阶段机住在 `agents/` 却在 `plugins/` 层被用）
  已全部消除；`stages.ts` 与 `prompts/` 已下沉到 `server/core/`。
  这条边界由 `npm run check:layers` 在 CI 里守着，违反会直接让流水线红。
