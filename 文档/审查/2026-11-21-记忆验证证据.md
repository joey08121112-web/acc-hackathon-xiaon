# 记忆验证证据（缩小版）

- **日期**：2026-11-21
- **依据**：`MEMORY-DESIGN-GUIDE.md` §7 第 8 项「验证要求」与 §8「诚实边界」
- **脚本**：`outputs/xiaon/scripts/agent/memory-verification.ts`（`npm run memory:verify`）
- **原始数据**：`2026-11-21-记忆验证证据.json`（同目录）
- **CI 覆盖**：`outputs/xiaon/tests-agent/i/memory-verification.test.ts` 每次 CI 都跑一遍

## 为什么有这份文件

2026-11-21 的全项目审查（`2026-11-21-全项目设计原则审查.md` §4.4）发现：记忆准则要求的
S1 / S3 / S10 缩小版验证**一次都没跑过**。记忆准则 §7 第 8 项写得很清楚：

> MVP 后至少跑 S1（新会话回忆）、S3（偏好覆盖更新）、S10（开销测量：C0 无记忆 / C1 装载 / C2 满档，ABBA×3 取中位数）；
> 跨天记忆保持需 24h/7d 延迟实验，一次会话不能证明"长期"；
> 未跑验证前禁止宣称"有效/大幅提升"。

现在它跑过了。

## 结果

| 场景 | 结果 | 说明 |
|---|---|---|
| **S1 新会话回忆** | 通过 | 写入 → 关库 → 重新打开（= 新进程的新会话）→ 档案与学习记忆都还在，且真的进了**出站上下文**（`profileBrief` / `context().memories`），不只是数据库里有 |
| **S3 偏好覆盖更新** | 通过 | 同一条偏好改了以后，出站上下文里只剩新的一条；旧的那条标失效保留（`itemHistory()` 能查到），没有被原地覆盖 |
| **S10 开销测量** | 通过 | 中位数：C0 无记忆 **0.104 ms** / C1 装载 8 条 **0.277 ms** / C2 满档 120 条 **0.792 ms** |
| **跨天保持 24h / 7d** | 通过 | 可控时钟推进 24 小时与 7 天后，记忆仍在，且仍然进出站上下文 |

### 怎么测的

- **S1**：用真实磁盘上的 SQLite（不是 `:memory:`），写完把库关掉再打开，模拟进程重启。
  核对的是**下一次实际出站上下文**里有没有它 —— 只查数据库不算数（PRD FR12 的验收口径）。
- **S3**：`chatUpdate` 走「失效不删」路径，旧条目标 `invalidated_at` 保留，新条目指向旧条目。
- **S10**：条件顺序按 ABBA×3（C0,C1,C2,C2,C1,C0），每个条件 6 次采样取中位数；
  测的是「读库 + 组装出站简报」这一段的耗时。
- **跨天**：用 `TestClock` 推进时间，不真的等 24 小时 —— 验证的是**时间规则**，不是"等得起"。

## 诚实边界（这段不能省）

这次验证的是记忆的**机制**：记住了吗、覆盖对不对、代价多大、跨天保不保得住。

它**不**证明「记忆让学习效果变好」。那需要带对照组的实验（不同学生分组、预先定义的成功指标、
样本量与统计方法），本文件没有做，**也不据此宣称效果**。

S10 的数字是**这台机器、这个数据量**的数字。换机器、换磁盘、换条目长度都会变；它能说明的是
「带着记忆出站的代价在毫秒量级，不会成为对话的瓶颈」，而不是一个可对外承诺的性能指标。
