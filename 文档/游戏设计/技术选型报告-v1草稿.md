# 游戏渲染/引擎技术选型报告（v1 草稿）

2026-10-28｜对比对象：SVG+DOM、Phaser 3、three.js 最小体素、完整 3D（Babylon 等）｜唯一可写产出：本文件。

**结论先行：推荐 SVG+DOM（React 19 声明式渲染 + CSS/Web Animations/rAF 动画）作为 P0 唯一游戏表现路线；Phaser 预批准为「触发条件命中后」的继任路线，three.js 体素与完整 3D 本期放弃。**

判断依据的五条判据来自任务书；三条研究/工程文档（研究 04、研究 05、工程 01）为只读引用，未修改。所有外部数据核验日期均为 2026-10-28。本报告为静态分析 + 官方文档核验，**未在真机 390×844 上实测任何引擎帧率，也未实际构建含引擎的 bundle**——这两项见 §7 待验证清单。

## 4. 推荐路线：SVG+DOM（P0 唯一游戏表现层）

### 4.1 为什么是它

1. **P0 场景就在它的舒适区正中央。** L1 温室水路 = 6×4 交点网格 ≈ 24 交点 + ~29 条边 + 管件/装饰物件 + 预算/记录表——交互元素总量几十个。SVG/DOM 与 Canvas 的性能分界共识是「少量元素 SVG 持平或更优、成百上千连续动画才让位 Canvas」（[JointJS](https://www.jointjs.com/blog/svg-versus-canvas)、[yWorks](https://www.yworks.com/blog/svg-canvas-webgl)、[MSDN](https://learn.microsoft.com/en-us/archive/msdn-magazine/2012/june/web-dev-report-working-with-graphics-on-the-web-canvas-vs-svg)，核验 2026-10-28）。P0 需要的动画是「试水时水流沿路径流动、叶片恢复」级别的过渡反馈，CSS transition / Web Animations 足以胜任。
2. **离线交付渠道零伤害。** 产品分发形态是「微信发一个 HTML 文件」（`outputs/team/双击打开-学伴小N.html`，364KB）。SVG+DOM 增量 0 字节；引入任一引擎都会让这个文件至少翻倍（Phaser）到十五倍（Babylon）。`build-offline.mjs:13` 的单 bundle 校验和 `:36` 的外部资源禁令对现有方案完全无感。
3. **团队已在此模式上工作，且零游戏经验的约束被最小化。** `ProfessionalMap.tsx`、`ExplorationMap.tsx`、`Art.tsx`（524 行 SVG 美术）证明声明式 SVG+DOM 是团队的既有工作方式；工程 01 `:45` 指出吉祥物 SVG 及其情绪/触摸体系可直接复用。App.tsx（3151 行）本来就面临拆分重构——在重构当口再引入「命令式引擎 + React 桥」的双世界心智模型，是把两个风险叠乘。
4. **可达性与研究 05 的要求天然对齐。** 研究 05 `:90` 要求「文字、按钮、键盘/触摸替代在 DOM 层」。SVG+DOM 的每个元素天然可聚焦、可加 ARIA、可被屏幕阅读器访问；Canvas/WebGL 里的内容对辅助技术是黑盒，需要额外重造可达层。
5. **不锁死未来。** 研究 04 `:269` / 研究 05 `:92` 已把「确定性规则模型与渲染解耦」定为架构不变量：任务定义（JSON+zod schema）、事件类型、求解/校验与渲染无关。P0 用 SVG 渲染这套模型，未来某场景切 Phaser 或 3D 时**重写的只是渲染层**，规则引擎、契约、服务端校验全部保留。这直接削弱了「现在就上 Phaser 以免日后迁移」的论点——迁移成本已被架构设计限制在渲染层内部。

### 4.2 P0 实施形态（L1 温室水路映射）

- 交点/边/管件 = SVG 图元（`<rect>`/`<line>`/`<path>`/`<g>`），由 zod 校验的任务 JSON 驱动 React 渲染；
- 拖放与点选 = Pointer Events + transform（不触发 layout），单击放件/长按拆件优先于自由拖拽（更符合 C 线「搭、试、改」，也回避移动端拖拽精度问题）；
- 试水反馈 = CSS transition / Web Animations 沿路径的流动动画 + 记录表 DOM 更新；
- 规则（`delivered = max(0, 8 - 2×leakCount)`、预算、退款）= 纯 TS 确定性模块，与渲染解耦，node:test 可测（沿用 `src/domain.test.ts` 模式）。

### 4.3 性能护栏（自我约束，违反即触发 §5 切换条件）

| 护栏 | 量化阈值 | 原因 |
|---|---|---|
| 动画属性 | 只用 `transform` / `opacity` | 走合成器路径，避免逐帧 style recalc / layout |
| 单屏常驻交互元素 | ≤ ~150–200 个 | DOM 舒适区；P0 用量 ~50，余量 3–4 倍 |
| 常驻 rAF 循环 | 默认无（动画由 transition/WAAPI 驱动，结束即停） | 移动端省电；现有代码无渲染循环的惯例延续 |
| 列表型内容 | 虚拟化或分页（试验记录表按场次折叠） | 避免长 DOM 树 |

真机验证要求：P0 合入前在 iPhone 级设备（390×844、DPR3）实测拖放帧率与内存，纳入验收（本报告未做，见 §7）。

## 5. 继任触发条件：何时切 Phaser（预批准，其余路线不预批准）

以下任一命中且经真机数据确认，单个场景可岛式接入 Phaser（官方 [phaserjs/template-react-ts](https://github.com/phaserjs/template-react-ts) 的 React+Vite+TS 模式：canvas 岛承载活动，文字/菜单/可达性仍留 DOM），并按研究 05 `:91` 避免双引擎长期并行：

1. 单场景**常驻动画**元素 > ~150–200，或需要逐帧 sprite/粒子系统；
2. 需要**镜头卷轴**世界（超出 C 线「单屏/少量场景」定义，如大地图连续漫游）；
3. 需要瓦片地图/纹理图集级内容密度，SVG 资产维护成本反超。

届时采纳的应是 **Phaser v4 线**（npm `phaser` latest = 4.2.1，2026-07-09；官方声明对 v3 标准用法 near drop-in，[phaser.io 公告](https://phaser.io/news/2024/11/phaser-v387-and-v400-released)，核验 2026-10-28），而非已冻结的 3.x。切换预算：包体 +356KB gzip、离线交付物约 ×4–5，需重新评估分发渠道（zip 体验包当前 117KB，`outputs/xiaon/dist/team/学伴小N-队友体验包.zip`）。

## 6. 放弃理由（逐条路线）

### 6.1 Phaser 3（现为 v4 线）——放弃于本期，预批准为继任

- **版本线困境（小团队维护成本）**：任务书指名的 Phaser 3 已冻结——3.x 最后版本 3.90.0（2025-05-23），npm `phaser` 主包 latest 已是 4.2.1（2026-07-09，registry 核验 2026-10-28）。现在引入 3.x = 选择一条不再接收修复的冻结线；直接上 4.x = 与任务书不符且 v4 稳定线仅约一年（RC1 2025-04→4.2.0 2026-06）。两者都给小团队留下版本决策债。
- **对 P0 过重（栈适配+单文件）**：P0 是 6×4 网格拖放，Phaser 的核心价值（sprite/相机/瓦片/粒子/物理）一项都用不上，却要先付出 +1,375,080 B min / +356,203 B gzip（phaser@4.2.1，bundlephobia 核验 2026-10-28；`hasSideEffects: true`，tree-shaking 受限）与「命令式引擎嵌入 React 树」的桥接复杂度（useEffect 生命周期、StrictMode 双挂载处理）。
- **研究文档的位置**：研究 05 `:91` 把 Phaser 放在「复杂动画/场景」档位，研究 04 `:30` 说「极简单网格也可先用 SVG/DOM」——P0 恰是极简单网格。Phaser 不是被否定，是被正确地排在了后面。

### 6.2 three.js 最小体素——放弃

- **官方教程只给了一半答案**：three.js 官方 voxel 教程（研究 05 引用的 [E04](https://threejs.org/manual/pages/voxel-geometry.html)，本轮核验 2026-10-28）明确只覆盖网格生成（面剔除、分块、UV 图集、射线拾取 demo），原文自述「not a game engine — no physics, collision, player movement, or game logic」——碰撞、输入、相机控制、游戏循环全部自研。对零游戏基础的团队（工程 01 `:42`），这是三条引擎路线中**自持引擎代码量最高**的选项。
- **路线错位（C 线匹配判据）**：体素 3D 是研究 04 的 **B 线**，其启动条件是「儿童行为证明自由旋转/高低层次是任务价值所必需」（研究 04 `:28`）——该证据尚不存在（游戏化实现度为零，工程 01 `:45`）。提前采纳等于绕过研究结论。
- **兼容性无回退（移动端判据）**：three.js r163（2024-04）起移除 WebGL1，**只支持 WebGL2 且无 Canvas 回退**（[Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration)、[r163 发布讨论](https://www.reddit.com/r/threejs/comments/1b3shok/threejs_finally_drops_support_for_webgl_10)，核验 2026-10-28）。面向儿童旧设备的移动端产品里，对比 Phaser 的 `AUTO`（WebGL→Canvas 回退）这是实打实的设备覆盖损失。
- **AI 状态可知性劣化**：研究 04 `:22-23`——3D 状态空间大、可行动作多，模型容易幻觉物件/不可能任务；C 线的紧凑可验证状态是选它的核心理由之一。
- 包体（184,898 B gzip 全量、tree-shake 后更小）反而是三条引擎路线里问题最小的——放弃它的原因不是体积，是路线错位 + 自研量 + 无回退。

### 6.3 完整 3D（Babylon 等）——放弃，五判据全败

- **离线单文件判据：直接冲突（否决项）**：`@babylonjs/core@9.32.1` = 8,184,453 B min / 1,817,335 B gzip（bundlephobia，2026-10-28）——离线交付物从 ~0.4MB 涨到 ~6MB+（原始体积 ×~15）。更硬的冲突：Havok 物理是**运行时加载的独立 WASM 模块**（官方文档 [HavokPlugin](https://doc.babylonjs.com/features/featuresDeepDive/physics/havokPlugin/)，核验 2026-10-28，`await HavokPhysics()` 异步取 wasm 实例），`build-offline.mjs:13,36` 的「恰好一个 script+style、无外部资产」不变量无法容纳独立 wasm 文件；base64 内联 wasm 属于体积自残的黑客手段。
- **移动端判据：儿童设备硬伤**：Havok 要求 WebAssembly SIMD，**iOS < 16.4 不支持**（同上官方文档）——家庭旧 iPhone/iPad 是儿童教育产品的常见机型。且完整 3D 的移动端视距/光照/发热正是研究 04 `:21` 标记的最高性能风险。
- **C 线匹配判据：这是 A 线**：研究 04 `:25-26` 估算 A 线 16–28+ 人周、「不推荐首发」；「三维资产和大量交互组合，内容成本最高」（`:22`）。
- **栈适配**：无官方 React 集成，命令式场景图需自建桥接层。
- 结论：五判据无一及格，且其中两项（单文件、设备兼容）为结构性冲突而非优化空间。

## 7. 本报告未做 / 待验证事项（如实声明）
