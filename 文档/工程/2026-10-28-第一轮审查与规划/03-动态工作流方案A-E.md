# 03 · 动态工作流方案 A–E（2026-10-28）

## 一、ZCode 动态工作流能力核验（实测，非假设）

核验方式：加载 `dynamic-workflows` 技能文档（含完整编译器门面 §16）+ `EvalWorkflowSnippet` 实跑只读片段 + `ListSavedWorkflows`/`ListWorkflowRuns` 查询。**实测结果：片段 900ms 编译执行成功**，真实读到仓库状态（8 份研究文件、main 分支、9 个未提交文件、55 个 agent 测试文件）。

已核验可用的操作（作为工作流的构件）：

| 能力 | 实测/文档依据 | 用途 |
|---|---|---|
| `CreateWorkflow`（script/saved/path 三种来源，编译期类型检查+运行前用户确认） | 技能 §16.1 | 启动工作流，每次运行前你会看到确认窗 |
| `agent()` 子代理 + 类型化结果 + 人设 | §16.2 facade | 分析/设计/评审的并行工作者 |
| `phase()` 阶段图 | §8 | 你在确认窗看到的节点图 |
| `files.glob/read/grep`、`git.changedFiles/diff/status/log`（只读、可重放） | 实测通过 | 工作流自取仓库事实 |
| `world.run`（确定性命令门，退出码即结论） | §5；`npm --prefix outputs/xiaon run test:agent` 可作测试门 | 测试/构建门控 |
| `channel`/`future`（流水线）、有界循环 | §7 | 逐文件→逐条目的流水线 |
| `hole<T>()`（运行中补写后续阶段） | §15 | 形状未知时先跑已知部分 |
| 子代理升级提问 → `ResolveWorkflowQuestion`（我转达或直接答） | §14 | 运行中的人工决策点 |
| `artifact.file/markdown/chart/table/board`（产物卡片+仪表盘） | §10 | 你直接打开的交付物 |
| `SaveWorkflow`（项目级 `.zcode/workflows/*.dwf.ts`，带参数声明，可反复按名运行） | §16.5；当前 0 个已保存 | A–E 的复用形态 |
| `AmendWorkflow`（热缓存修订）、`ResumeWorkflowRun`（断点续跑） | §13/16.4 | 出错恢复 |
| `EvalWorkflowSnippet`（同步试跑台） | 实测通过 | 脚本入库前验证固定逻辑 |

**边界（同样实测确认）**：子代理不能嵌套启动工作流；工作流脚本是纯 TS 沙箱（无 fs/fetch/process）；每次 CreateWorkflow 运行需你确认；保存工作流需你同意后写入仓库。

## 二、总体依赖与触发关系

```
研究成果导入/更新 ──► A 产品研究同步 ──┬──► B 综合模式设计与验证 ──┐
（文档/研究/...）      （需求矩阵 vN）    ├──► C 专业模式与游戏引擎研究 ─┼──► 实现轮（每轮先过 E 门）──► 反馈回 A/B/C/D
                                        └──► D AI架构与数据系统 ──────┘         │
任意代码改动/部署前 ──────────────────────────────► E 质量评审与持续验证 ◄──────┘
```

- A 是唯一入口：矩阵版本号是 B/C/D 的公共输入（`args.matrixPath`）。
- E 独立触发（基线/每轮实现后/部署前），是唯一会跑 `world.run` 测试门的工作流。
- 实现轮不在 A–E 内：工作流只产出「已核证的方案文档」，业务代码修改在你批准方案后由主会话或专用实现工作流执行（见 04）。

## 三、五个工作流规范

通用约定（五个都适用）：
- **触发**：由你或我在主会话点名启动（如「跑一次研究同步」）；每次运行前 ZCode 弹确认窗（即第一道人工审批）。
- **写权限**：只写 `文档/` 下的新文件（A 另建 `文档/产品|架构|游戏设计|测试/`），**不改 `outputs/xiaon` 业务代码、不改已有文档**。
- **质量检查**：产物必须含「已核证/未核证」分区；每条结论带 `路径:行号` 或研究文件引用；关键发现由独立子代理复核（换人复审）。
- **恢复**：脚本错→`AmendWorkflow`（热缓存，只重付改动部分）；中断/断电→`ResumeWorkflowRun`；子代理卡在只有你能答的问题→升级提问转达。
- **交接**：所有产物登记进 `文档/产品/需求矩阵-vN.md` 的「产出索引」节 + 最终 `return` 结构化报告（conclusion/findings/verified/notCovered）。

### 工作流 A · 产品研究同步（`xiaon-research-sync`）

| 项 | 内容 |
|---|---|
| 触发 | 新研究材料入 `文档/研究/`，或矩阵需升版 |
| 输入 args | `researchDir`（默认 `文档/研究/2026-10-28-教育产品深度研究`）、`matrixVersion` |
| 实际工具 | `files.glob` 盘点 → 每份研究文件一个解析子代理（typed：需求条目/假设/开放问题）→ 每条需求一个代码核证子代理（grep 证据定位）→ 汇总子代理合成矩阵 → `artifact.markdown` 发布 |
| 步骤 | ①盘点文件与规模 ②逐份解析（8 路并行）③需求↔代码双向核证（已实现/部分/未实现/相抵触）④登记 H01–H11 待验证假设 ⑤合成矩阵+发布 |
| 输出 | `文档/产品/需求矩阵-v1.md`（每条需求：ID/描述/研究出处/代码核证状态/涉及模式/优先级建议）+ 待验证假设清单 |
| 质量检查 | 抽样 20% 需求由独立子代理反向核对「研究是否真这么说」；无出处的条目一律不入矩阵 |
| 人工审批 | 矩阵发布为**草稿**，你确认后标 v1 定稿（升级提问确认）；此后 B/C/D 只认定稿版 |
| 交接 | 定稿即解锁 B/C/D 并行 |

### 工作流 B · 综合模式设计与验证（`xiaon-comprehensive-design`）

| 项 | 内容 |
|---|---|
| 触发 | 矩阵定稿后；或对话策略相关需求变更 |
| 输入 args | `matrixPath`（A 的定稿矩阵） |
| 实际工具 | 现状分析子代理（读 `stages.ts/roles.ts/learning.ts/plugins/*`）→ 策略设计子代理（研究 03 九动作 ↔ 现有阶段机映射）→ 职责划分评审子代理（Agent 工具 vs 普通函数，沿用「程序能判不给模型」原则）→ 测试集生成子代理（基于 03 §60 场景模板）→ 独立评审子代理（换人挑毛病） |
| 步骤 | ①对话系统现状事实表 ②意图路由与动作协议设计（增量，不重写阶段机）③观察/记忆更新规则草案（含维度扩展口径）④对话测试集 v1（场景 JSON + 0–3 量规锚例）⑤独立评审并修订 |
| 输出 | `文档/产品/综合模式技术方案-v1.md` + `文档/测试/对话测试集-v1.json`（+量规） |
| 质量检查 | 方案每条须映射矩阵需求 ID；测试集过 schema 校验（`EvalWorkflowSnippet` 先验证解析逻辑）；评审子代理以「哪里会坏」提问而非「是否可行」 |
| 人工审批 | 方案文档交你批准后，实现任务才进开发队列（本轮明确不动代码） |
| 交接 | 测试集交 E 作回归输入；实现后的效果验证回填矩阵 |

### 工作流 C · 专业模式与游戏引擎研究（`xiaon-game-research`）

| 项 | 内容 |
|---|---|
| 触发 | 矩阵定稿后；或你决定启动专业模式升级时 |
| 输入 args | `matrixPath` |
| 实际工具 | 选型对比子代理（SVG/DOM vs Phaser vs 体素 B vs 3D：bundle 体积/移动端 390×844/离线单文件约束/维护成本，WebSearch 取官方证据）→ 玩法评审子代理（研究 04 的 15 候选 × 首切片标准）→ 规格细化子代理（温室水路状态机/事件/数据结构/Agent 交互协议）→ 风险与不变量子代理（INV-01..10 对照）→ 独立评审 |
| 步骤 | ①前端适配事实核查（复用 01 §3 结论并更新）②选型矩阵 ③温室水路实施版规格（含两条见证解的程序验证方案）④与现有 map/interview 页的关系（并存 or 替换）⑤风险清单 |
| 输出 | `文档/游戏设计/技术选型报告-v1.md` + `文档/游戏设计/温室水路原型规格-v1.md` |
| 质量检查 | 每个选型结论必须列放弃的替代方案与理由；规格逐条对照 INV-01..10；见证解（5 边直线/7 边绕行）由规格子代理给出可程序重放的表述 |
| 人工审批 | 选型结论与规格交你批准（这决定后续 D1–D3 开工范围） |
| 交接 | 规格交 D（数据模型/工具面）与实现轮；E 据此建游戏域测试框架 |

### 工作流 D · AI 架构与数据系统（`xiaon-arch-data`）

| 项 | 内容 |
|---|---|
| 触发 | 矩阵定稿后；或架构相关决策待立时 |
| 输入 args | `matrixPath`；可选 `focus`（arch/data/privacy/cost） |
| 实际工具 | 架构审计子代理（roles/tools/registry vs 研究 05 路线）→ 游戏工具面子代理（5 只读工具映射 registry 模式）→ 数据模型子代理（新增实体草案进契约扩展 diff）→ 隐私合规子代理（个保法/拟人化办法/未成年人条例对照，含 chatLog 保留期）→ 成本子代理（复用研究 05 §11 公式按真实单价重算）→ 独立评审 |
| 步骤 | ①现状架构与研究方向差异表（预计差异极小——已天然对齐）②游戏域实体与 API 草案（MissionDefinition→TransferProbe）③隐私对照表（含 ADR-005 决策素材）④成本模型 ⑤ADR 草案 |
| 输出 | `文档/架构/架构与数据模型-v1.md`（含 mermaid 图）+ API 方案 + ADR 草案集 |
| 质量检查 | 每个新增实体给出 zod 草案并被独立子代理对照现有 `entitySchemas` 命名/迁移惯例检查；隐私表逐条给「现状/要求/差距/工作量」 |
| 人工审批 | ADR 草案逐条交你决策（adopt/pending/reject） |
| 交接 | 定稿 ADR 并入 05-技术决策记录.md；实体草案是实现轮 D1 的直接输入 |

### 工作流 E · 质量评审与持续验证（`xiaon-quality-gate`）

| 项 | 内容 |
|---|---|
| 触发 | 三种模式：`baseline`（当前树全量基线）/ `feature`（某轮改动后）/ `release`（部署前） |
| 输入 args | `mode`、`scope`（改动路径列表，feature 模式用） |
| 实际工具 | `world.run` 确定性门（`npm --prefix outputs/xiaon run test` / `test:agent` / `typecheck:agent` / `build`；Playwright 按需）→ 验收核对子代理（按 04 的验收标准逐项，typed findings）→ 高危发现独立复核子代理 → 报告合成 |
| 步骤 | ①跑快门（单测+类型）②跑强门（test:agent 全量；release 模式加 build+浏览器套件）③验收标准逐项核对（含 INV 不变量抽查）④问题分级 P0–P3 + 回归清单 ⑤发布报告卡片 |
| 输出 | `文档/测试/质量报告-<日期>-<模式>.md` + 问题清单（含修复优先级） |
| 质量检查 | 门是命令不是模型断言（退出码即结论）；高危发现必须独立复核或标 unconfirmed；报告必须区分「未检查」与「检查了没发现问题」 |
| 人工审批 | 运行本身无审批（只读+测试）；但报告中的**修复动作**逐条批准后才执行 |
| 交接 | 绿→放行实现轮合入/部署；红→问题回流对应工作流或实现轮 |

## 四、落盘与首跑计划（待你批准）

1. 我将五个工作流分别 `SaveWorkflow` 到项目级 `.zcode/workflows/`（写入仓库，随 git 版本化），带上述 args 声明——**此步需你点头才开始写文件**。
2. 首跑顺序：E(baseline) 先行（拿到全量测试基线，顺便验证 chatLog 改动）→ A（矩阵）→ 定稿后 B/C/D 并行。
3. 每次运行你都会看到脚本确认窗（含阶段图与将执行的命令集）；运行中升级的问题我会原样转达。
4. 复用性：矩阵升版、每轮实现、每次部署都按名重跑对应工作流；`AmendWorkflow` 保证改脚本不重付已完成的分析。

## 五、不放进工作流的事（明确边界）

- 业务代码修改：永远在方案获你批准后，由主会话/专用实现工作流执行，E 只验收。
- 真实儿童测试、招募、外部服务操作：不自动化，按研究 06 §6 的人工流程列步骤。
- 部署/提交/推送：保持现有人工确认习惯，工作流不持有 git 写能力（facade 的 git.* 本身只读，world.run 命令集在确认窗可见）。
